## 한 문단 소개

Cut & Check는 Python을 가르치지 않습니다. **모호한 요청을 검증 가능한 단계로 바꾸는 법**을
가르칩니다. 우리가 믿는 건 하나입니다 — 문제를 쪼갤 줄 아는 아이는 실패했을 때
"나는 못한다"가 아니라 "세 번째가 틀렸다"고 말합니다. 그 차이가 그 아이가 이 과목에
남을지를 결정합니다.

---

## 왜 문제를 쪼개는 능력이 필요한가

**1. 분해는 효율 장치가 아니라 자존감 보호 장치다.**
문제를 통째로 붙들고 실패하면 원인이 자기 자신이 됩니다. 능력 탓으로 귀인하는 순간
그 학생은 그 과목을 떠납니다. 쪼개면 "나는 못한다"가 "세 번째 주문서에서 내 기준이
안 맞았다"로 바뀝니다. 앞은 사람에 대한 판결, 뒤는 방법에 대한 정보입니다.

**2. 쪼개지 않으면 내가 틀렸는지 확인할 방법이 없다.**
"주문서를 정리한다"는 판정할 수 없습니다. "쉼표로 자른다"는 판정할 수 있습니다 —
쉼표 없는 주문서를 넣어보면 되니까요. 조각을 내는 행위가 곧 검증 지점을 만드는 행위입니다.

**3. 컴퓨터는 아이가 만날 수 있는 가장 정직한 청중이다.**
사람은 빈칸을 메워줍니다. 컴퓨터는 안 메워줍니다. 그래서 생각의 구멍이 드러납니다.
Python은 이 훈련을 시키는 가장 값싼 장치일 뿐, 목적이 아닙니다.

> 일반적인 사고력 향상(far transfer)은 **주장하지 않습니다.** 근거가 약하고,
> 반박당하면 서비스 전체가 흔들립니다. 대신 코드가 아닌 도메인 미션(미션 03)으로
> 전이를 제품 안에서 증명합니다.

## 설계 원칙과 화면 구현

| 원칙 | 화면 구현 | 빼면 생기는 일 |
|---|---|---|
| 문제 정의 = 종료 조건 정하기 | 1단계. 업무 요청은 일부러 모호하게. 성공 조건을 고르기 전까지 2단계 잠김 | 문제 정의가 `완료`로 찍힌 채 시작되고 학생은 받아쓰기만 함 |
| 분해는 나누기가 아니라 기준 정하기 | 2단계. 자를 기준 + **"왜 그걸 골랐나요?"** 필수 | `split(",")`은 버튼 한 번 누르기가 되고 사고는 0이 됨 |
| 시작 비용 0, 판단 대행 0 | 빈 화면 없음. **틀린 순서로도 실행됨** | 교사가 가이드 코드를 띄우고, 수업이 필사가 됨 |
| 한 번 맞히는 건 통과가 아니다 | 실행 = 입력 3장 동시. 마지막 한 장은 반드시 반례 | 하드코딩이 걸러지지 않음 |
| 피드백은 평가가 아니라 거울 | 학생이 고른 성공 조건을 결과 옆에 다시 띄우고 자기가 판정 | 채점 주체가 플랫폼이 되고 학생은 정답 추측을 시작함 |
| "안 돼요"는 어휘의 부재 | 도움 요청이 **증상 진술 폼**으로 대체 | 교사가 화면을 처음부터 읽어야 하고 26명을 감당 못 함 |
| 인정은 사람, 증거는 기계 | 에러는 위치만. AI는 칭찬하지 않고 되묻기만 함 | 사람의 격려가 싸구려가 됨 |

### 의도적으로 넣지 않은 것

- **포인트 · 연속 출석 · "좋아요!" 팝업** — 칭찬을 기계에 넘기면 사람의 격려가 싸구려가 된다
- **정답 순서 대조 채점** — 채점하는 순간 학생은 우리 답을 추측하기 시작한다
- **다음 블록 추천** — 판단 대행의 가장 흔한 형태
- **힌트·코드 보기 먼저** — 증상을 말하기 전에 주면 말할 이유가 사라진다
- **방법을 지시하는 체크리스트** — "쉼표를 기준으로 나누기"는 요구사항이 아니라 정답 공개다

## 미션 구성

| # | 단계 | 내용 | 지원 수준 |
|---|---|---|---|
| 01 | 분해 | 주문서를 상품 단위로 자르기 | 기준도 보기, 이유도 보기 |
| 02 | 반복과 조건 | 알레르기 주의 재료만 걸러내기 | 기준은 보기, 이유는 직접 쓰기 |
| 03 | 다른 세계에서 | **코드가 아닌 문제** — 실험 계획서에서 위험 단계 뽑기 | 기준까지 직접 쓰기 |

미션 03이 전이 주장의 증명 장치입니다. 블록은 그대로인데 세계만 바뀝니다.

### 반례 설계

각 미션의 마지막 입력은 학생의 기준을 깨뜨리도록 설계돼 있습니다.

| 미션 | 반례 | 무엇이 드러나는가 |
|---|---|---|
| 01 | `사과 바나나 우유` (쉼표 없음) | 기준이 이번 입력에만 통했다는 사실 |
| 02 | `사과, 바나나, 물` (주의 재료 0개) | 결과를 하드코딩했는지 여부 |
| 02 | 잘린 조각 앞의 공백 (`" 우유"`) | 눈에 안 보이는 차이도 컴퓨터에겐 다른 값이라는 것 |
| 03 | `관찰하기 → 기록하기` (위험 단계 0개) | 같은 논리가 다른 세계에서도 버티는지 |

## 실행

빌드도 의존성도 없습니다. 정적 파일만 있습니다.

```bash
git clone https://github.com/tomchaccom/Cut-Check.git
cd Cut-Check
open index.html          # 또는 브라우저로 드래그
```

GitHub Pages를 켜면 `index.html`이 그대로 데모가 됩니다.

### 엔진 검증

```bash
node test/engine.test.js
node test/hangul.test.js
```

미션별 정답 순서가 통과하는지, 반례가 실제로 깨지는지, 블록을 빠뜨렸을 때
**정확히 몇 번 블록을 지목하는지**를 검사합니다.

### 리뷰할 때

화면 우측 상단 **`설계 의도 보기`** 를 켜면 각 UI 요소가 어떤 원칙을 집행하는지
주석이 붙습니다. 리뷰는 이 상태로 보시는 걸 권합니다.

## 다음에 증명해야 할 것

1. **현장 검증** — 증상 진술 완성률, 교사 개입당 소요 시간. 지표는 아래.
2. **사전 설문** — 학생이 어디서 막히는지, "안 될 때 가장 먼저 하는 행동"의 분포.
3. **미션 04 이후** — 추상화(변수·함수) 단계. 지금은 03까지.

### 측정 지표

- **증상 진술 완성률** — 도움 요청 중 기대값·실제값을 둘 다 채운 비율.
  초반엔 20%도 안 나올 것으로 예상. 이 숫자가 올라가는 게 제품이 일한다는 증거.
- **1단계 보기 분포** — 하드코딩·요행 보기를 고른 비율이 곧 위험군 규모.
- **교사 개입당 소요 시간** — 학교 도입의 실질 세일즈 포인트.
