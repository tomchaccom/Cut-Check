# 커리큘럼과 지원 페이딩

## 1. 사고 과정과 Python 문법의 관계

문법과 사고력 요소를 일대일로 동일시하지 않는다. 사고는 문제를 푸는 과정이고,
문법은 그 사고를 표현하는 도구다.

| 사고 과정 | 의미 | 표현 도구 |
|---|---|---|
| 문제 정의 | 끝났다는 걸 어떻게 아는지 정하기 | 성공 조건 문장 |
| 기준 정하기 | 어디서 끊을지 결정하기 | 구분자 선택 |
| 데이터 분해 | 하나를 여러 조각으로 나누기 | `split()` |
| 반복·패턴 인식 | 같은 작업을 여러 데이터에 적용하기 | `for` |
| 조건 분기 | 상황에 따라 다른 경로 선택하기 | `if` |
| 추상화 | 공통 구조를 재사용 가능하게 만들기 | 변수, 함수 |
| 평가·디버깅 | 결과를 확인하고 수정하기 | 반례 입력, 증상 진술 |

`split()`은 분해 사고력 그 자체가 아니라 나누는 도구다.
**사고가 일어나는 지점은 `split`이 아니라 `","`를 고른 판단이다.**

## 2. 미션 구성

| # | 단계 | 세계 | 학생이 결정하는 것 |
|---|---|---|---|
| 01 | 분해 | 주문서 정리 | 성공 조건, 자를 기준 |
| 02 | 반복과 조건 | 알레르기 검수 | + 기준을 고른 이유를 직접 서술 |
| 03 | 다른 세계에서 | **과학 실험 계획서** | + 자를 기준을 직접 입력 |
| 04 | 추상화 | 02와 03을 나란히 | + 무엇이 달라지는지 직접 고르기, 이름 직접 짓기 |

미션 03은 코드가 아닌 도메인이다. 블록은 그대로고 세계만 바뀐다.
**이게 전이 주장의 증명 장치이며, 빠지면 전이를 주장할 자격이 없다.**

미션 04는 앞의 두 미션을 재료로 쓴다. 처음 보는 예시 두 개를 들고 오면
"원래 비슷한 걸 골라왔겠지"로 끝난다. **자기가 직접 해본 일이어야 같은 구조라는 게 몸으로 온다.**

### 미션 04에서 추상화를 가르치는 방식

변수와 함수를 먼저 가르치지 않는다. 추상화는 *두 일에서 같은 구조를 알아보는 것*이고,
변수와 함수는 그걸 적는 도구일 뿐이다. 그래서 순서가 이렇다.

1. 두 업무를 나란히 놓고 "같은 일인가"를 묻는다 (어떤 답이든 통과시킨다)
2. **무엇이 달라지는지 학생이 직접 고른다**
3. 고른 것에만 이름을 붙인다 — 이름 후보는 제안하지 않는다
4. 같은 함수로 두 업무를 돌린다

핵심 장치는 2번이다. **학생이 고른 것만 변수가 된다.** 덜 고르면 그 값은 첫 번째 업무의
값으로 굳어서 두 번째 업무에서 무너지고, 굳어버린 값이 생성된 코드 안에 따옴표로 박혀
그대로 보인다. 무엇을 빠뜨렸는지 문장으로 말해주지 않는다 — 코드가 증거다.

## 3. 지원 페이딩

"어디까지 지원할 것인가"는 고정값이 아니라 함수다. 단계가 올라갈수록 지원을 걷어낸다.

| | 미션 01 | 미션 02 | 미션 03 | 졸업 과제 |
|---|---|---|---|---|
| 성공 조건 | 보기 3개 + 직접 쓰기 | 보기 4개 + 직접 쓰기 | 보기 3개 + 직접 쓰기 | 직접 쓰기만 |
| 자를 기준 | 칩으로 선택 | 칩으로 선택 | **직접 입력** | 직접 입력 |
| 고른 이유 | 보기 3개 | **직접 서술** | 직접 서술 | 직접 서술 |
| 블록 상자 | 필요한 것 위주 | 불필요한 블록 섞임 | 전부 | 전부 |
| 증상 진술 | 보기 전부 제공 | 보기 + 자유 서술 | 자유 서술 | 자유 서술 |
| 반례 입력 | 자동 투입 | 자동 투입 | 자동 투입 | **학생이 직접 설계** |

마지막 칸이 핵심이다.

> **졸업 과제: "이 논리를 깨뜨릴 입력을 네가 만들어봐."**

반례를 스스로 만들 수 있으면 그 학생은 명세화 능력을 획득한 것이고,
그 능력은 Python 밖에서도 그대로 쓰인다.

## 4. 한 미션 안의 학습 순환

1. **정하기** — 이 일이 끝났다는 걸 어떻게 확인할지 먼저 정한다
2. **선언하기** — 어디서 자를지, 왜 그렇게 정했는지 말한다
3. **조립하기** — 블록으로 순서를 만든다 (틀린 순서도 실행된다)
4. **버텨보기** — 입력 3장으로 한 번에 돌린다. 마지막 한 장은 반례다
5. **판정하기** — 내가 쓴 성공 조건을 내가 들고 결과를 판정한다
6. **말하기** — 깨졌다면 어디서 왜 깨졌는지 문장으로 만든다
7. **고치기** — 자를 기준을 다시 정하고 4번으로 돌아간다. 고친 이력이 남는다

3번과 4번 사이에 "정답 확인" 단계가 없다는 점이 중요하다.
플랫폼은 맞았는지 알려주지 않고, 결과만 보여준다.

## 5. 반례 설계 원칙

각 미션의 마지막 입력은 학생의 기준을 깨뜨리도록 설계한다.
반례는 네 가지 축 중 하나를 건드린다.

1. **개수 변화** — 상품이 3개에서 4개로 (하드코딩 적발)
2. **구분자 변화** — 쉼표가 없는 입력 (기준의 일반성 검증)
3. **빈 결과** — 걸릴 게 하나도 없는 입력 (결과를 미리 적어둔 학생 적발)
4. **보이지 않는 차이** — 앞뒤 공백 (`"우유"` vs `" 우유"`)

4번은 특히 중요하다. 엔진은 공백을 **일부러 봐주지 않는다.**
봐주면 학생은 "눈에 똑같아 보여도 컴퓨터에겐 다른 값"이라는 개념을 평생 만나지 못한다.

## 6. 평가 방향

정답률이 아니라 사고 단계별 병목을 본다.

**컴퓨팅 개념** — 변수 / 반복 / 조건 / 데이터 형태
**컴퓨팅 실천** — 문제 정의 / 기준 선언 / 논리 구성 / 디버깅 / 일반화
**컴퓨팅 관점** — 자기 논리 설명 / 다른 풀이 비교 / 도구로서의 컴퓨터 인식

### 교사 화면이 보여줄 것

정답률이 아니라 이것들이다.

- 1단계에서 **하드코딩·요행 보기를 고른 학생 명단** (위험군)
- 2단계에서 **"그냥 골랐어요"를 고른 학생 명단**
- 증상 진술 큐 — 학생이 무엇을 기대했는지가 문장으로
- **칭찬 타이밍** — 스스로 깨진 곳을 찾아낸 순간

"학생이 막혔다"는 교사가 이미 안다. 팔리는 정보는 *무엇을 기대했는지*다.

## 7. 측정 지표

| 지표 | 정의 | 왜 보는가 |
|---|---|---|
| 증상 진술 완성률 | 도움 요청 중 기대값·실제값을 둘 다 채운 비율 | 제품이 일한다는 직접 증거 |
| 위험군 비율 | 1단계에서 하드코딩·요행 보기를 고른 비율 | 수업 설계 조정 신호 |
| 교사 개입당 소요 시간 | 호출부터 해결까지 | 학교 도입의 실질 세일즈 포인트 |
| 반례 자작 성공률 | 졸업 과제에서 자기 논리를 깨뜨리는 입력을 만든 비율 | 명세화 능력 획득 여부 |
