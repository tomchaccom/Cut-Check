# 설계 카드 · 코드 뼈대 · 생성 검수 — 설계

날짜 2026-10-16 · 브랜치 `tomchaccom/card-design` · 결정은 대화에서 사람이 했다 (아래 "결정" 절)

## 왜

AI 가 만든 미션을 학생 화면에서 따라가 보니 (eval 미션 "중복 항목 세기", 420px 캡처):

1. **문제를 봐도 뭘 하는지 모른다.** 요청이 "목록을 보고 수를 세어 보세요." — 무슨 수인지 없다.
   첫 화면엔 자료 1개만 보인다. 자료끼리 이야기가 다르다 (과일 / 문구 / 둘이 섞인 반례, 이름도 겹침).
2. **성공 조건 보기가 무슨 뜻인지 모른다.** "하나로 정한 기준이 맞으면 성공" — LLM 이 쓴 문장.
   코드의 기본 문장("겹치는 건 한 번만 센 수가 나오면 성공")은 분명하다.
3. **"어떻게 할까?" 가 빈칸 시험지다.** "같은 목록은 [선택하기].", "[항상 숫자 3]만 보여준다."
   보기가 답지처럼 보이고, 학생은 설계가 아니라 우리 답을 맞힌다.

그리고 학생이 고른 방법은 지금 실행되지 않는다 (`renderRunStep` 은 호출되는 곳이 없다).
설계는 코드 단계 위의 요약과 교사 기록에만 쓰인다 — 그래서 실행 가능한 형태일 필요가 없다.

## 결정 (사람)

| 질문 | 결정 |
|---|---|
| 설계 단계 형식 | **동작 카드를 골라 순서 정하기** (빈칸 문장 폐기) |
| 카드에 무엇까지 | **동작 + 필요한 카드만 세부 고르기** + 설계도가 **코드 에디터에 주석 뼈대**로 들어간다 |
| LLM 과 코드의 몫 | **LLM 은 이야기, 판단의 뼈대는 코드** |
| 생성 직전 검수 | **LLM 검수 → 탈락 시 재생성 최대 2번 → 그래도 탈락이면 교사 검수 필요** |
| 기본 문장형 미션 4개 | 같은 카드 화면으로 옮긴다 |
| 카드 순서 바꾸기 | 위·아래 화살표 버튼 (끌어 놓기 아님 — 휴대폰·키보드) |

## 1. 생성: 누가 무엇을 쓰나

| 칸 | 쓰는 쪽 | 비고 |
|---|---|---|
| 제목, 상황, 요청, 항목 이름, 자료 2개(이름·내용), 반례 이름, 걸러낼 대상·이름 | LLM | 수업 주제에 맞는 이야기 |
| 성공 조건 보기 | 코드 | `CORRECT[key]` 에 항목 이름만 끼운다. 함정 둘(이번 결과, 에러만 안 나면)은 지금처럼 코드 |
| 설계 카드 · 세부 보기 · 헷갈리는 카드 | 코드 (`js/core/cards.js`) | 미션의 `pipelineId` 로 정해진다. 미션 데이터에 카드를 싣지 않는다 |
| 반례 내용 | 코드 | 이미 그렇게 바뀌었다 (PR #31) |

- LLM 스키마(`_ask_schema`)에서 `goals` · `sentences` 칸을 뺀다. 검사 모델(`DRAFTS`)과 `_fallback` 에서도 뺀다.
  지금 남은 기본 틀이 전부 `sentences` 라 이 실패 원인이 통째로 사라진다.
- **요청 문장 규칙 추가:** 구할 값을 생활 말로 쓴다 ("몇 가지", "모두 얼마", "가장 큰", "순서대로").
  방법(나누기·중복 빼기 등)은 여전히 쓰지 않는다. 검사기 `_brief_problem` 에 "구할 값이 없음" 을 더하고,
  같은 말을 스키마 설명에 쓴다 (검사기와 설명이 어긋나면 모델이 못 맞춘다 — PR #30·#31 의 교훈).

## 2. 카드 카탈로그 (`js/core/cards.js`, core 층)

연산 하나 = 카드 하나 = 코드 한 줄(쯤). 문구는 학생 1인칭 동작 명사형.

| 연산 | 카드 | 세부 보기 |
|---|---|---|
| split | 나누기 | 기준: 쉼표 / 공백 / 줄바꿈 |
| filter | 골라내기 | {걸러낼 대상 이름}에: 있는 것만 / 없는 것만 |
| filter (숫자 유형) | 글자 빼기 | — |
| toNumber | 숫자로 바꾸기 | — |
| transform | 항목마다 다듬기 | 앞뒤 공백 없애기 / 첫 글자만 남기기 |
| unique | 겹친 것은 하나만 | — |
| sort | 순서대로 늘어놓기 | 가나다순 / 거꾸로 |
| join | 다시 이어 붙이기 | 이을 때: 쉼표 / 공백 |
| count | 개수 세기 | — |
| sum | 모두 더하기 | — |
| max / min | 가장 큰 값 찾기 / 가장 작은 값 찾기 | — |
| groupCount | 항목마다 몇 번인지 세기 | — |

- **헷갈리는 카드 1장:** 그 유형에 없는 연산 중 하나를 고정 표(`DECOY[pipelineId]`)로 고른다 —
  무작위가 아니어야 교사가 같은 화면을 본다. 예: `split-unique-count` → 순서대로 늘어놓기.
- **세부 보기에 "항상 숫자 3" 같은 대놓고 틀린 보기를 넣지 않는다.** 셋 다 그럴듯해야 한다.
- **채점하지 않는다.** 카드 순서·세부를 정답과 대조하지 않는다 (CLAUDE.md "정답 블록 순서와 대조하는 채점").
  틀린 설계는 코드를 반례로 돌릴 때 학생이 스스로 발견하고 "설계 수정" 으로 돌아온다.
- 카드 표는 core 에 한 벌. Python 은 카드를 모른다 (서버는 `pipelineId` 만 낸다).

## 3. 학생 화면 (`sentence.html` · `js/ui/sentence.js`)

| 단계 | 바뀐 뒤 |
|---|---|
| 1 뭘 해야 할까? | 요청 + **자료 2개** (반례는 지금처럼 코드 단계에서) |
| 2 언제 성공일까? | 코드가 쓴 보기 — 진짜 조건 1~2 + 함정 2. 고른 이유 칸은 그대로 |
| 3 어떻게 할까? | 카드 목록(진짜 + 헷갈리는 1장, 섞인 순서는 고정)에서 골라 "내 설계도" 칸에 넣고, ▲▼ 로 순서, ✕ 로 빼기. 세부가 있는 카드는 카드 안에서 고른다. 고른 이유 칸 그대로. 카드 1장 이상 + 세부 다 고르면 다음 |
| 4 코드로 만들기 | 에디터가 비어 있으면 설계도를 주석 뼈대로 넣는다 (아래) |

```python
# data 에 자료가 들어 있어요.
# 1. 나누기 (기준: 쉼표)

# 2. 겹친 것은 하나만

# 3. 개수 세기

```

- 함수 이름(split·set·len)은 보여주지 않는다 — 문법은 튜터에게 묻는다.
- 학생이 이미 코드를 쓴 뒤 설계를 고치면 **덮어쓰지 않는다.** 에디터가 비었거나 이전 뼈대 그대로일 때만 새 뼈대로 바꾼다.
  (고친 이력은 화면 위 설계도 요약에 남는다 — "고치는 문을 막지 않는다")
- 기본 문장형 미션 sm1·sm2·sm3 에 `pipelineId` 를 붙여 같은 카드 화면을 쓴다 (sm-filter-1 은 이미 있다).
  어느 유형인지는 각 미션의 정답 슬롯으로 정한다 — 구현 계획에서 미션별로 확인.
- 빈칸 문장 UI(`select.slot`, `#sent1~3`)와 쓰이지 않는 `renderRunStep` 은 지운다.

## 4. 생성 직전 LLM 검수 (`api/_review.py`)

미션을 다 조립한 뒤(학생이 볼 문장 그대로) LLM 을 한 번 더 부른다. structured output:

```json
{"understand": {"ok": true, "why": "..."},   // 중1이 요청을 읽고 구할 값을 아는가
 "sameStory":  {"ok": true, "why": "..."},   // 세 자료가 같은 이야기인가
 "noAnswer":   {"ok": true, "why": "..."},   // 문제 문장에 답·방법이 드러나지 않았나
 "easy":       {"ok": true, "why": "..."}}   // 쉬운 말로 짧게 썼나
```

- 넷 다 ok → 통과.
- 하나라도 아니면 → **이유를 붙여 처음부터 다시 생성** (재생성 최대 2번, 즉 검수 최대 3번).
- 3번째도 탈락, 또는 남은 시간이 모자라면 → 가장 최근 미션에 `guard.review = {status: 'teacher', reasons: [...]}`.
- 검수 호출 자체가 실패(504 등)하면 → 검수 없이 `status: 'teacher', reasons: ['검수를 못 했어요']`.
- **시간:** Vercel 함수 60초. 생성 ~8초, 검수 ~3초. 재생성은 남은 시간이 25초 넘을 때만.
  `DEADLINE` 은 생성 한 번이 아니라 요청 전체에 건다.
- 교사 화면: 초안에 "검수 필요" 배지 + 이유 목록. 확정은 교사가 한다 (막지 않는다).
- 학생에게는 보이지 않는다. 검수 문장은 교사만 본다.

## 5. 기록 · 교사 화면

- `s-design` 에 `cards: [{op, detail}]` 를 더한다. `slots` 는 예전 기록 읽기용으로 남긴다.
  기존 필드의 의미가 바뀌는 게 아니라 스키마 버전은 그대로 (CLAUDE.md "새 이벤트를 더할 때" 4).
- `fold.js` 의 `sDesign` 에 `cards` 를 담는다. 교사 상세의 설계도 표시는 카드 순서·세부로.
- 교사 미션 초안 화면: 성공 조건 보기·카드 미리보기·검수 배지.

## 6. 테스트 · 평가

- `test/layer.test.js` 또는 새 `test/cards.test.js`: 14개 유형 모두 카드가 나오고, 헷갈리는 카드는 그 유형에 없는 연산이고,
  세부 보기에 금지 문구(판정·칭찬·"항상")가 없다. 카드 문구는 `llmguard` 실제 문장 검사에도 넣는다.

  통과 / 1번 탈락 후 통과 / 3번 탈락 → teacher / 검수 호출 실패 → teacher / 시간 부족 → 재생성 없음).

- `test/robust.js`: 카드 세부·이유가 교사 화면까지.
- `test/eval_generate.py`: 검수 1차 통과율, 재생성 횟수, teacher 로 넘어간 비율을 요약표에 더한다.
